# 地図座標と他艦ワールド位置の調査

2026-11-01。0.2.3の実機検証中に行った読み取り調査。
この調査ではゲーム用ソースや導入済みファイルを変更していない。

## 現在の座標取得フロー

`Main.py` の `_collect_map_positions` は、dataHubのavatarエンティティから
`avatar.playerId`（なければid）と `mapPosition.position` の2D値、yawを読む。
これをプレイヤーIDでbattle.getAllShips由来の艦船情報に対応付ける。
読み出しは既存の定期スナップショット内で行われる。

`_map_norm_xy` は2D値を0～1前提で検査する。
-0.01～1.01の外は不採用、その内側のわずかなはみ出しは0～1へ丸める。
採用した値を `ships[].nx/ny` として出力する。
この処理自体が正規化方式を発見しているわけではなく、既存コードの前提である。

ワールド位置は `_get_ship_position` → `_position_from_obj` で、
Ship.getPosition、position/worldPosition/positionHull、プレイヤー情報などを試す。
取得失敗は例外を握りつぶし、最終的にNoneとする。
従って現ログだけでは「APIなし」「例外」「None」「ベクトル変換失敗」を区別できない。
`_component_pos` という補助関数はあるが、現在この関数を呼ぶ経路はない。
worldPositionコンポーネントを実際に読んでいると勘違いしないこと。

ワールド位置が得られない艦は、地図→ワールドの較正が成立していれば補完する。
較正未成立でも地図座標があればvisible=trueで出力し、positionは省略される。
この「visible」は実装独自の判定で、3D描画中を保証しない。

## 他艦positionがnull/欠落する理由

現方式は同一フレームにある `(mapX,mapY,worldX,worldZ)` の対を集め、
3隻以上で較正する（`_fit_map_transform`）。

しかしb01/b02/b03/b06/b07、with-atm-b01/b02/b03の対象戦闘は、
全フレーム `diag.mapSamples=1`、`diag.mapCalib=null`。
他艦には地図座標がある一方、ワールド位置は得られていない。
このため較正条件を満たせず、地図座標からの補完も永久に動かない。

「直接の取得経路で他艦のworld位置が取れていない」ことと、
「較正方式が自艦1隻しか使えない環境に対応していない」ことの2層に分ける。
前者がゲームの公開制限なのか、取得方法の不足なのかは未確定。

## 記録からの時系列較正の試算

自艦については同じ艦を別時刻で追跡すると、地図/world両方の組が多数取れる。
discardedを除外し、各記録の最後の戦闘について、各軸を最小二乗で試算した。
以下の数値は生ワールド座標単位であり、メートルではない。

| 記録 | worldX ≈ a*nx+b（a/b） | worldZ ≈ c*ny+d（c/d） | 軸別RMSE x/z |
| --- | --- | --- | --- |
| without-atm-b01 | 1199.247 / -599.427 | -1199.383 / 599.527 | 0.117 / 0.149 |
| without-atm-b02 | 1199.109 / -599.646 | -1199.652 / 599.756 | 0.051 / 0.099 |
| without-atm-b03 | 1199.454 / -599.660 | -1200.539 / 600.089 | 0.021 / 0.102 |
| without-atm-b07 | 1201.099 / -600.778 | -1200.522 / 600.075 | 0.025 / 0.106 |
| with-atm-b01 | 1198.571 / -599.477 | -1199.020 / 599.464 | 0.011 / 0.090 |
| with-atm-b02 | 1198.747 / -599.599 | -1199.141 / 599.564 | 0.010 / 0.099 |
| with-atm-b03 | 1197.230 / -599.012 | -1198.546 / 599.302 | 0.008 / 0.075 |

対象試験の地図はOcean。概ね `worldX=1200*(nx-0.5)`、
`worldZ=1200*(0.5-ny)` という関係を支持するが、
この定数を他地図へハードコードしない。丸め・更新時差等も未分離。
b06は自艦が動いておらず、同じ位置の繰り返しなので時系列較正にも使えない。

さらに前半だけで係数を推定し、後半を未使用検証データにすると、
without-atm-b01のx/z RMSEは0.111/0.229、with-atm-b03は0.009/0.118。
時系列サンプルの利用は有望だが、これは同じ艦の同じ地図での検証であり、
敵艦のworld位置との独立照合や他地図での検証の代わりにはならない。

## 現在の較正ロジックの注意点

- 同一フレームの3隻が必要で、自艦の移動履歴を貯めない。
- 軸を入れ替えた2モデルを比べるが、独立軸ごとのスケール+平行移動だけで、
  任意の地図回転を含む一般の2Dアフィン変換ではない。
- 最小の残差モデルを選ぶだけで残差や係数の受入閾値がなく、最初の結果を固定する。
- 一直線のサンプルでは3点以上あっても軸方向を一意に識別できない場合がある。
- 地図からworldへ補った位置のyは0固定。潜水艦深度を取得したという意味ではない。
- `_collect_map_positions` の可視フィルターは `mapVisible is False` のみ。
  数値0・属性欠損・最終目撃マーカーの扱いが十分かは実機確認が必要。
- map座標があるだけで現在可視と判定し、最終目撃キャッシュを更新する。
  未発見艦の古いマーカーが残る場合に「現在位置」と混同する危険がある。

## 次の実装候補（未実装）

1. 直接world取得の各経路に、成否・None・変換失敗を分けた診断を追加する。
2. mapPositionの生値、可視フラグ、取得元を明示し、現在/最終目撃を分離する。
3. 自艦の時系列サンプルを戦闘単位で蓄積し、十分な移動と軸の独立性を満たしてから較正。
   停船・一方向だけの移動・地図切替・異常値では未較正のままにする。
4. 保留サンプルで誤差を検証し、係数・誤差・サンプル数・位置のderived由来を出力する。
5. 魚雷ワールド座標→正規化地図座標も同じ変換で検証する。

これにより、他艦が地図座標しか持たなくても、較正成立後は
魚雷と艦船を同じ2D平面で扱う道筋ができる。
