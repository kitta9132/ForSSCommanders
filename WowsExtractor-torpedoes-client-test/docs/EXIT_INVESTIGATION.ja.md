# 戦闘から訓練ルームへ戻れない問題の調査

## 比較条件と確定していること

- build 13357625、ATM退避済み。
- 0.2.0導入状態で、戦闘→訓練ルーム復帰時に無限ロードという報告。
- WowsExtractorだけをPnFMods外へ退避した比較では退出成功。
- よってWowsExtractor単体または他modとの相互作用を重点調査する。
  1回の比較だけで単独原因や再現率は確定しない。
- 0.2.1は開始イベント順の修正。退出不能が直ったとは未確認。
- b01/b02/b03の記録はすべてactive:falseで終わる。
  b03の終了取得は22:41:13頃、SessionStats例外は22:41:14頃。
  退出ハンドラが終了フレーム出力まで到達したことと整合するが、
  後続のUI遷移が成功したことを示さない。
- 次回は0.2.1再導入の結果を比較するため、監査中の追加コード変更は行わない。

## 優先して切り分ける箇所

1. **終了・退出イベントと定期収集の境界**
   現在onBattleQuitでのみ停止し、onBattleEndは購読していない。
   終了後から退出通知まで、破棄途中のbattle/dataHubを読む可能性はある。
   ただし終了通知と手動退出の順序は未確認で、これだけで原因とはいえない。
2. **コールバック取消**
   callbacks.cancel(handle)の利用方法は公式資料に一致する。
   例外を握りつぶし、取消失敗時もhandleを失うため診断できない。
   取消自体がゲーム内で停止する場合は、Python例外対策だけでは検出できない。
3. **退出ハンドラの同期処理**
   _stop_tick、BallisticsTracker.stop、ローカル状態リセット、
   DamageTracker.snapshot、終了JSONの直列化・保存が同じイベント内で走る。
   各段階の開始・終了ログがないため、現ログだけでは停止位置を特定できない。
   ダメージsnapshotはローカル辞書を処理し、直接ゲームAPIを呼ばない。
4. **同期ファイル出力**
   既存ログにasync writer enabled/async writer unavailableはともにない。
   従って非同期writerが動作した証拠はなく、同期出力の可能性が高い。
   終了フレームのactive:falseは記録済みだが、UI復帰成功を意味しない。
5. **他modとの相互作用**
   22:41:14にSessionStatsがKeyError: elite_expを出している。
   同時刻にゲーム側では訓練ルーム作成・データ更新が続いている。
   画面の無限ロードとサーバー/ゲーム処理の完全停止は区別する。
   SessionStats例外が原因・結果・無関係のどれかは未確定。

## 原因と断定できないもの

- 開始時write failed for Noneは実在する別の問題で、0.2.1で対策済み。
  退出不能との因果関係はまだない。
- _AsyncWriterは終了時joinを呼んでおらず、join待ちデッドロックの経路はない。
  ロック/スレッド一般の問題すべてを否定したわけではない。
- _tryで例外を捕まえても、C++/ゲームエンジン側の待ち・停止は防げない。
- JSONファイル監視ツールはゲーム状態を書き換えない。
- 提出記録に終了フレームがあることだけで「正常退出」と評価してはいけない。

## 再現した場合の次の段階

- onBattleStart/Shown/End/Quit、cancel前後、終了出力前後を低頻度ログで可視化する。
- 機能を一度に変更せず、終了JSON保存、砲弾追跡、魚雷弾パラメータ取得、
  UI HP/dataHub読み取りを個別に停止できる診断版で比較する。
- WowsExtractorだけの環境と既存mod併用環境を比べる必要が出た場合は、
  他modを勝手に退避せず、可逆な切り替え方法を用意してから実施する。
